> 目标：从 Python 后端开发转向 AI Agent 应用开发
>
> 时间预算：每周 10-15 小时
>
> 学习方式：先接任务、独立实现、提交验收，再按问题补知识

## 新的学习规则

这份计划不再按“阅读理论 -> 记笔记 -> 跟着示例写代码”推进，而是按真实开发流程推进：

1. 每一关先拿到一个可运行项目的需求、约束和验收标准。
2. 你负责查资料、选型、编码、运行命令、测试和提交代码。
3. 我只提供方案，不直接替你实现或操作。
4. 遇到问题时，你先给出错误信息、相关代码、已尝试方法和自己的判断。
5. 我给排查顺序、原因提示和可选方案；除非你明确改变规则，否则不提供可直接粘贴的完整实现。
6. 验收通过后再复盘，只补本次项目真实用到的原理。

### 我每一关会提供什么

- 业务背景和用户故事
- 功能范围与明确的不做项
- 技术约束、接口约定和建议目录
- 分阶段任务清单
- 验收用例和完成定义
- 必要资料的检索关键词
- Code Review 结论和下一轮改进方向

### 你每一关需要提交什么

- 可运行的代码仓库
- 启动方式和环境说明
- 实际测试结果，而不是“理论上可以”
- 一个简短复盘：最难的问题、你的解决过程、仍然不确定的地方

## 通过标准

不再用“看完多少文档、写了多少笔记”衡量进度。每一关只有三种状态：

- **未运行**：代码尚未形成完整闭环。
- **可运行**：主流程能跑通，但异常处理、测试或工程质量不足。
- **已通过**：验收用例通过，能解释关键取舍，别人按照 README 可以启动。

每周只追求一个可验证成果。博客、算法题和额外阅读均为可选产物，不阻塞主线。

## 第一阶段：做出最小闭环（第1-4周）

### 第1关：命令行流式对话助手

**任务**：开发一个 Python CLI 对话助手，接入一个 OpenAI 兼容模型 API。

**必须实现**：

- API Key 从环境变量读取，仓库中不得出现密钥。
- 支持 system prompt、连续多轮对话和流式输出。
- 能限制历史消息长度，避免上下文无限增长。
- 对超时、鉴权失败、限流和网络异常给出可读提示。
- README 能让一位新用户在 10 分钟内运行起来。

**验收**：连续完成 5 轮对话；断网或使用错误密钥时程序不崩溃；Git 历史中没有密钥。

### 第2关：从零实现最小 RAG

**任务**：让应用根据一组本地 Markdown/TXT 文档回答问题，并给出引用来源。

**约束**：第一版不使用 LangChain 的整条 RAG 链封装。你需要亲自连接“读取 -> 切分 -> Embedding -> 存储 -> 检索 -> 组装提示词 -> 回答”各步骤。

**验收**：

- 至少导入 10 篇文档，并能重复执行导入。
- 回答包含来源文件名和对应片段。
- 问题在资料中没有答案时，不编造结论。
- 提供至少 10 个测试问题及实际结果。

### 第3关：RAG 效果评测与优化

**任务**：不增加花哨功能，先证明检索效果确实变好了。

**必须实现**：

- 建立不少于 30 条的评测集，标注期望命中的文档。
- 比较至少 3 组 chunk size、overlap 或 top-k 参数。
- 记录命中率、回答正确率、延迟和单次调用成本。
- 根据数据选择默认参数，并写出选择理由。

**验收**：评测可通过一个命令重复运行；优化结论有数据支持。

### 第4关：带工具调用的 Agent

**任务**：在 RAG 之外增加至少两个真实工具，例如计算器、数据库查询、时间查询或内部业务 API。

**必须实现**：工具参数校验、调用日志、超时处理、错误返回，以及最大执行步数限制。

**验收**：准备 15 个场景，覆盖直接回答、单工具、多工具、工具失败和禁止操作；Agent 的行为与预期一致。

## 第二阶段：把 Demo 做成服务（第5-8周）

### 第5关：Agent API 服务

把前一阶段能力封装为 FastAPI 服务，提供健康检查、对话、流式对话和会话查询接口。加入请求校验、统一错误格式、日志、pytest 集成测试和 Docker 启动方式。

**验收**：全新环境可用一条 Docker 命令启动；自动化测试覆盖主流程；两个会话的数据不会串线。

### 第6关：面向生产的 RAG

给服务加入 BM25 + 向量混合检索、重排、文档增量更新、删除和知识库隔离。用第3关评测集证明变化，并观察质量、延迟和成本之间的取舍。

**验收**：不同知识库不可互相检索；更新文档后无需全量重建；新方案至少在一个核心指标上有明确提升，且没有无法接受的回退。

### 第7关：MCP 工具服务

把一个真实能力封装为 MCP Server，例如查询 CRM 客户信息、搜索内部文档或创建待办事项。选择一个支持 MCP 的真实客户端完成连接和调用。

**验收**：工具描述清晰、参数有校验、错误可观察；客户端能完成至少 5 个成功用例和 3 个失败用例。

### 第8关：LangGraph 工作流

实现一个必须使用状态机才有价值的流程：信息收集 -> 检索 -> 判断证据 -> 调用工具 -> 人工确认 -> 执行 -> 总结。流程需支持中断、恢复和执行步数限制。

**验收**：进程中断后可以从检查点恢复；高风险工具未经人工确认不会执行；每个节点的输入输出可追踪。

## 第三阶段：交付一个真实产品（第9-12周）

综合项目暂定为“企业知识库与业务操作助手”。如果届时工作中出现更真实的问题，可以替换题目，但必须保留下列工程要求。

### 第9周：先设计，再写骨架

从真实用户的 3 个高频任务出发，完成一页 PRD、范围边界、架构决策记录、数据模型、API 契约和风险清单。随后建立可运行骨架和 CI，不提前堆功能。

**验收**：需求能用用户行为描述；每个核心接口有请求、响应和错误示例；空项目可以在 CI 中完成构建和测试。

### 第10周：完成核心业务闭环

完成文档上传与管理、检索问答、引用溯源、会话记录，以及至少一个会改变业务数据的工具操作。高风险操作必须先确认。

**验收**：一个新用户可以从空数据开始完成完整流程；刷新页面或重启服务后关键数据仍存在；失败后不会留下半完成数据。

### 第11周：可靠性和部署

建立离线评测与关键路径测试，加入结构化日志、请求追踪、超时重试、限流和成本记录。用 Docker 部署到可访问环境，并完成 HTTPS 配置。

**验收**：线上完成 20 个真实任务；主要失败能从日志定位；README 中的部署步骤经重新验证。

### 第12周：产品打磨和项目表达

邀请至少 2 位真实用户试用，根据反馈修复最影响使用的 3 个问题。完成演示脚本、架构图、核心取舍、指标结果、项目复盘和简历项目描述。

**验收**：5 分钟内可以稳定演示核心价值；能清楚回答“为什么这样设计、哪里失败过、数据如何证明有效、下一步怎么做”。

## 实战中补基础的方法

CS 基础不再单独排课，而是在工程问题出现时补齐：

| 项目现象 | 当场补的知识 |
|---|---|
| 流式响应中断、接口超时 | HTTP、SSE、TCP、超时与重试 |
| 检索慢、数据重复 | 索引、时间复杂度、幂等性 |
| 多会话串数据 | 并发、事务、隔离级别、状态管理 |
| Agent 无限循环 | 状态机、终止条件、图遍历 |
| 服务重启后任务丢失 | 持久化、消息队列、检查点 |
| Docker 中无法访问服务 | 进程、端口、网络、DNS |

只学解决当前问题所需的最小知识，然后立刻回到项目验证。面试前再根据项目中的真实案例整理成系统答案。

## 每周节奏

- **任务下发**：我给本周场景、约束、拆分和验收标准。
- **独立实现**：你完成编码、命令操作和初步测试。
- **卡点求助**：你提交最小复现和自己的判断，我给排查方案。
- **项目验收**：我按用例检查代码与运行结果，只指出问题和修改目标。
- **复盘过关**：你完成修正并解释取舍，然后进入下一关。

如果一周时间不足，就缩小功能范围，但不能跳过运行、测试和复盘。没有验收通过的项目不靠阅读更多资料来掩盖，也不同时开启新的主线项目。

- 1 个已部署、有人试用的 AI Agent 产品。
- 4 个可以独立运行的阶段项目：RAG、Tool Agent、MCP Server、LangGraph 工作流。
- 一套有真实问题和指标的 RAG 评测集。
- 自动化测试、日志、Docker、部署和故障排查记录。
- 能围绕自己的代码解释技术原理和工程取舍。
