今天完成了 `cli-chat` 的功能闭环，也推进了 `minimal-rag` 的主体实现。两个项目已经可以组合运行：在同一个命令行程序中，既能进行普通多轮对话，也能切换到本地 Vue 文档知识库问答。

不过，“代码链路跑通”和“项目验收完成”不是同一件事。`cli-chat` 已完成当前功能目标；`minimal-rag` 已具备核心链路和可用数据，但评测数量、结果记录与异常场景验证仍需补齐，所以目前仍属于**部分完成**。

## cli-chat：先把对话主流程做完整

`cli-chat` 是一个基于 Python 和 OpenAI 兼容接口的命令行聊天助手。它的代码不多，但已经包含一个对话应用最基本的工程要素。

### 1. 流式输出

模型返回的内容不是等待完整响应后一次性打印，而是逐块读取并实时输出。这样可以明显降低用户感知到的等待时间。

这里需要区分两个概念：**总响应时间**没有因此缩短，但**首字延迟**变短了。对聊天应用而言，后者往往更直接地影响使用体验。

### 2. 多轮上下文与历史截断

每轮成功对话都会把用户消息和助手回复加入 `messages`，下一次请求便能理解之前的上下文。程序最多保留最近 10 轮对话，避免历史无限增长。

截断上下文不仅是为了防止超过模型限制，还会影响三个实际指标：

- Token 成本：历史越长，每次请求重复发送的内容越多。
- 响应速度：输入 Token 增加会带来额外处理时间。
- 回答相关性：过多旧话题可能干扰当前问题。

### 3. 命令与错误边界

当前支持 `/clear`、`/exit`、`/quit` 等命令，并分别处理鉴权失败、限流、超时、连接失败和 API 状态错误。请求失败后程序会保留在交互循环中，而不是直接崩溃退出。

一个值得保留的细节是：只有模型成功返回后，当前消息才会写入历史。否则，失败的请求也进入上下文，可能让后续对话出现不完整或误导性的记录。

## minimal-rag：亲手连接 RAG 的每个环节

这次没有直接使用 LangChain 或 LlamaIndex 的完整 RAG 链，而是把流程拆成多个独立模块：

```text
本地文档
→ 加载与清洗
→ 按结构切分
→ 控制切片长度
→ Embedding 向量化
→ JSONL 持久化
→ 相似度与元数据加分排序
→ 构造带来源的提示词
→ 聊天模型流式回答
```

拆开实现的价值，是能看清 RAG 并不是一个单独的模型，而是一条数据处理和检索链路。最终回答质量不只取决于聊天模型，也取决于文档质量、切片粒度、Embedding、召回排序和提示词约束。

### 文档清洗与结构化切分

知识库使用 Vue 官方中文文档。加载后先移除无用注释和标题锚点，同时保留 Options API、Composition API 等上下文标记。切分时依据 Markdown 标题层级记录文档、章节、子章节和 API 模式，而不是只按固定字符数粗暴截断。

过长切片会进一步拆分到约 1200 字符以内，并保留少量段落重叠。代码块被视为完整单元，尽量避免从中间截断。

这里的关键知识点是：**chunk size 并非越大越好**。切片过大时，一个向量会混合多个主题；切片过小时，上下文又可能不足。重叠可以缓解边界信息丢失，但也会增加存储量和重复召回概率。

### 向量化与断点续传

切片会被批量发送到 OpenAI 兼容的 Embedding 接口，结果保存为 JSONL。向量构建时还会记录模型名称和输入内容摘要：如果切片内容与模型都没有变化，便直接复用已有向量。

这让重复构建具备了基本的增量能力，也能避免因为中途失败而从头支付全部 Embedding 成本。写入时先生成临时文件，再替换正式文件，降低数据文件损坏的风险。

### 检索与来源引用

查询先被转换为向量，再与本地全部切片计算余弦相似度。当前排序分数由向量相似度和标题、章节、API 模式等元数据加分组成。

余弦相似度关注的是两个向量的方向是否接近，而不是长度是否相同，常用于衡量文本语义接近程度。元数据加分则用于处理用户直接提到章节名或 API 模式的情况。当前方法适合小型知识库，但它还不等同于 BM25 与向量检索组成的真正混合检索。

取回 Top-K 切片后，程序会为资料编号，并要求模型：

1. 只根据检索资料回答；
2. 关键结论使用 `[来源 N]` 标注；
3. 资料不足时明确说明无法确定；
4. 在末尾列出实际使用的文件和章节。

引用格式能提升可追溯性，但“模型输出了引用”不代表引用一定正确。后续评测还需要检查引用编号是否真的支持对应结论。

## 两个项目如何连接

`cli-chat` 新增了一个独立适配层，只负责导入并调用 `minimal-rag` 的流式问答函数。这样命令行交互、普通聊天和 RAG 实现没有混在同一个模块中。

```text
用户输入
├─ 普通模式 → cli-chat → 聊天模型
└─ RAG 模式 → 适配层 → minimal-rag
                         ├─ 查询向量化与检索
                         ├─ 组装带来源提示词
                         └─ 聊天模型流式回答
```

使用 `/rag on` 和 `/rag off` 可以切换模式。RAG 检索只使用当前问题，不把整段聊天历史直接转换为检索向量，从而减少旧话题对当前检索意图的干扰。

两个项目目前共用仓库根目录的虚拟环境和 `.env` 配置模板，但普通聊天与 RAG 使用不同的环境变量前缀，既方便统一管理，也允许它们连接不同的模型服务。

## 为什么 minimal-rag 还不能算完成

核心代码和数据已经存在，但当前只有 6 条人工验证题，尚未达到计划要求的至少 10 条，并且还缺少可重复查看的实际评测结果。因此下一步不是继续增加新功能，而是补足证据：

1. 把检索验证题扩充到至少 10 条，覆盖不同文档和相似概念。
2. 为每道题记录 Top-K 实际命中、排名和是否足以回答。
3. 增加资料中没有答案的问题，验证系统是否稳定拒答。
4. 检查回答中的每个引用是否与对应切片一致。
5. 补充自动化测试，覆盖切分、余弦相似度、排序和提示词规则。
6. 重新按 README 从干净环境执行一次，记录完整验收过程。

## 今日最重要的认识

今天最大的收获并不是调用了两个模型接口，而是建立了对 RAG 工程边界的理解：

- 聊天模型负责基于上下文组织答案，Embedding 模型负责把文本映射到可比较的向量空间。
- 检索命中不代表回答正确，必须分别评估召回、排序、生成和引用。
- 模块拆分不是为了让目录看起来复杂，而是为了让每个阶段都能单独观察、调试和替换。
- “能运行”只是阶段成果；只有验收用例、实际结果和可重复步骤齐全，项目才算真正完成。

下一步会集中完成 `minimal-rag` 的评测与验收，再根据数据调整 chunk size、overlap 和 Top-K，而不是凭感觉继续堆功能。
