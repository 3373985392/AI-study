上一篇文章记录了 `cli-chat` 从命令行程序变成 Web Chat 的第一版过程。当时系统已经有邀请码门禁、SSE 流式输出、额度限制和浏览器界面，但聊天历史只保存在 `localStorage`，服务端不理解“会话”，也没有真正处理长对话问题。

从 8 月 4 日到现在，这套系统又完成了一次结构性升级。它不再只是一个带输入框的模型调用页面，而是开始具备一个小型聊天产品需要的状态边界：

- 同一个邀请码可以创建多个同步会话，并跨设备继续聊天。
- 用户仍可选择“仅本机”会话，正文不上传服务器。
- 普通聊天使用 Token 预算和滚动摘要处理长上下文。
- Vue 助手直接绑定本地 RAG，不再让用户理解底层模式开关。
- 新增独立的 `/admin` 管理员后台，可管理邀请码并查看同步历史。
- 人格成为会话级属性，产生消息后不再允许随意切换。
- 增加请求超时、SSE 心跳、使用指标、成本估算和 RAG 自动评测。

如果把两版系统放在一起比较，变化会更直观：

| 能力 | 8 月 4 日版本 | 当前版本 |
|---|---|---|
| 聊天历史 | 浏览器 `localStorage` | 同步多会话 + 仅本机会话 |
| 长上下文 | 固定保留最近若干轮 | Token 预算 + 结构化滚动摘要 + 最近原文 |
| 人格 | 聊天中随时切换 | 产生消息后锁定 |
| RAG | 手动切换模式 | Vue 助手自动使用 RAG |
| 邀请码管理 | 命令行工具 | 命令行 + 独立管理员后台 |
| 可观测性 | 基础结果记录 | 首 Token、总耗时、Token、成本和错误码 |
| 质量验证 | 单元测试 | 单元测试 + RAG Recall@K / MRR / 引用检查 |

## 一、先让服务端真正认识“会话”

第一版 Web Chat 由浏览器把历史消息随请求一起提交，服务端只完成一次无状态生成。这种方式实现简单，但有三个明显限制：

1. 换设备后无法继续原来的对话。
2. 清理浏览器数据后历史永久丢失。
3. 服务端无法稳定维护摘要、反馈和会话级设置。

这次在 SQLite 中新增了四组核心数据：

```text
conversations             会话标题、所属邀请码和人格
messages                  用户与助手的完整原始消息
conversation_memories     滚动摘要及摘要边界
message_feedback          助手消息的点赞和点踩
```

同步会话的请求链路变成了：

```text
浏览器发送 conversation_id 和当前问题
  → 服务端验证会话是否属于当前邀请码
  → 从数据库读取历史与滚动记忆
  → 按 Token 预算构造模型上下文
  → SSE 流式返回回答
  → 完整回答生成后保存一轮问答
  → 必要时更新滚动摘要
```

浏览器不再拥有同步会话历史的最终解释权。这样不仅能跨设备继续聊天，也避免客户端伪造另一会话的历史内容。

不过，并不是所有会话都必须上传服务器。页面仍然保留“新会话仅本机”选项：这类会话继续使用当前浏览器的 `localStorage`，不会进入服务器数据库，也不会出现在管理员后台。

这里形成了一个明确的隐私边界：

- **同步会话**：方便跨设备和长期记忆，正文默认保留 365 天，管理员可查看。
- **仅本机会话**：正文只留在当前浏览器，但无法跨设备恢复，也没有服务端滚动摘要。

登录页会直接披露这一区别，而不是把数据策略藏在实现细节里。

## 二、为什么固定窗口不适合长对话

最简单的上下文管理方式是只保留最近 N 轮。它能控制输入长度，但会产生一种很突兀的遗忘：某个项目名、用户偏好或已经确认的决定，只要滑出窗口就完全消失。

另一方面，把全部历史永久发给模型也不可行：

- 输入 Token 会持续增长。
- 请求延迟和调用成本越来越高。
- 最终仍会超过模型上下文窗口。
- 大量旧消息会稀释当前问题的重要信息。

当前方案采用三层结构：

```text
会话级系统人格
  + 较早对话的结构化滚动记忆
  + Token 预算内的最近完整问答
  + 当前问题
```

滚动记忆不是一整段随意生成的总结，而是固定为四类字段：

```json
{
  "summary": "当前对话的整体摘要",
  "facts": ["用户明确表达的事实"],
  "decisions": ["已经确认的决定"],
  "open_items": ["仍未完成的事项"]
}
```

当“已有记忆 + 尚未摘要的消息”达到阈值后，系统会压缩较早的一批消息，同时保留最近四轮原文。压缩只在完整问答边界结束，避免只总结用户问题却丢掉对应回答。

数据库还会记录 `summarized_through_message_id`。下次压缩时只处理这个边界之后的新消息，不会反复把全部历史塞给摘要模型。如果边界消息意外缺失，系统会清除不再可信的旧摘要，而不是继续叠加错误记忆。

模型请求也不再按固定条数裁剪，而是先预留：

```text
上下文窗口
- 最大输出 Token
- 安全余量
- 系统人格与滚动记忆
- 当前问题
= 可用于最近历史的 Token 预算
```

然后从最新消息向前，以完整问答轮次装入历史。这样小模型和大模型都可以复用同一套逻辑，只需调整上下文窗口配置。

## 三、记忆压缩需要额外模型吗

不一定。

当前实现支持单独配置 `LLM_MEMORY_MODEL`，但默认直接复用 `LLM_MODEL`。也就是说，第一版部署不需要再购买或维护一套独立模型服务。

```dotenv
LLM_CONTEXT_WINDOW_TOKENS=32768
LLM_MEMORY_TRIGGER_TOKENS=16000
LLM_MEMORY_RECENT_ROUNDS=4
LLM_MEMORY_MAX_INPUT_TOKENS=12000
LLM_MEMORY_MAX_OUTPUT_TOKENS=800
# 可选；不配置时复用主聊天模型
# LLM_MEMORY_MODEL=qwen-plus
```

摘要模型使用低随机性输出，并强制返回 JSON。服务端会验证字段类型、数组数量和文本长度，避免异常响应或无限增长的摘要进入后续上下文。

同时，滚动摘要会以“不可执行的历史资料”注入模型，明确要求它不能覆盖当前系统规则。这一点很重要，因为旧对话中可能包含类似指令的文本；记忆系统不能把用户历史提升成新的系统提示词。

记忆压缩属于派生能力。即使摘要调用失败，已经正常生成的回答仍然会保存，不会因为摘要失败而回滚整轮聊天。下一次请求仍可使用最近原始消息继续工作。

## 四、人格不应该成为每条消息的临时开关

当前页面提供三个入口：普通助手、Vue 框架助手和趣味人格。早期版本允许在聊天过程中随时切换，但历史消息仍然带有旧人格的表达风格，滚动摘要也可能保留旧人格影响。

这会造成一个典型冲突：系统提示词已经切换，模型看到的历史却仍然属于另一个人格。结果不是完全不生效，而是表现不稳定。

最终规则调整为“人格属于会话，而不是单条请求”：

- 新建且没有消息的会话可以选择人格。
- 一旦产生消息，人格按钮立即禁用。
- 页面提示“当前不允许切换人格，如需切换人格请新建对话”。
- 会话更新接口对已有消息的人格修改返回 HTTP 409。
- 修改标题仍然允许。

这个约束看似减少了自由度，实际提高了对话一致性。想换人格时新建会话，也能自然隔离旧历史和旧摘要。

其中“Vue 框架助手”不只是换了一段提示词，它会自动进入 `minimal-rag` 检索链路，返回本地 Vue 文档来源。用户选择的是任务角色，而不是底层技术模式。

## 五、新增独立管理员后台

邀请码数量增加后，只靠服务器命令行已经不方便。这次新增了不出现在公开导航中的 `/admin` 路由，管理员登录后可以：

- 搜索并分页查看所有邀请码。
- 查看状态、标签、分钟/日额度、最近使用时间和用量统计。
- 自动生成高强度邀请码，或创建符合规则的自定义邀请码。
- 修改标签与额度，启用或撤销邀请码。
- 查看某个邀请码下的同步会话和完整消息。
- 查看消息来源、反馈以及当前滚动记忆摘要。

管理员没有删除聊天消息或会话的能力。第一版后台只承担查看和访问管理职责，避免把高风险的数据删除操作混进日常管理界面。

管理员认证与普通邀请码认证完全隔离：

```text
普通用户：ai_chat_session
管理员：  ai_chat_admin_session
```

管理员密码不以明文保存，而是通过 Python 标准库 `scrypt` 生成自描述哈希：

```powershell
cd D:\myproject\projects\cli-chat
..\..\.venv\Scripts\python.exe -m app.admin_credentials hash
```

后台还使用独立的 `ADMIN_SESSION_TOKEN_PEPPER` 对随机会话令牌计算 HMAC 摘要。密码哈希发生变化后，旧管理员会话会因为凭据指纹不匹配而立即失效。

其他安全边界包括：

- 管理员 Cookie 默认有效期 8 小时。
- Cookie 使用 HttpOnly、SameSite=Strict，生产环境启用 Secure。
- 管理员登录按客户端地址限制失败次数。
- 普通邀请码 Cookie 不能访问管理员接口，管理员 Cookie 也不能冒充普通用户。
- 管理员响应设置 `Cache-Control: no-store`。
- 修改操作和聊天详情访问写入审计事件。
- 审计记录只保存动作、目标和必要元数据，不保存密码或聊天正文。
- 数据库仍然只保存邀请码 HMAC 摘要；自动生成的邀请码明文只在创建响应中展示一次。

## 六、可靠性和可观测性补齐

聊天服务增加了连接超时、读取超时、有限重试、最大输出 Token 和总生成时限。SSE 在模型长时间没有输出时发送心跳，减少代理或浏览器误判连接已经断开的概率。

每次调用会记录：

- 使用模型与人格。
- 成功、错误或客户端取消。
- 首 Token 延迟和总耗时。
- 输入、输出字符数与 Token 数。
- 按配置单价估算的调用成本。
- 归一化后的错误码。

这些指标与聊天正文分表保存。日志和统计可以回答“系统是否变慢、哪个人格成本更高、错误集中在哪一类”，但不会为了观测而复制用户消息内容。

部署层也做了收紧：聊天服务使用专用的 `ai-study` 无登录用户运行，Uvicorn 只监听本机地址，由 Nginx 对外提供 HTTPS 和反向代理。

## 七、RAG 从能回答走向可评测

`minimal-rag` 新增了独立评测入口：

```powershell
python -m src.evaluate --top-k 3
python -m src.evaluate --top-k 3 --generate
```

默认只调用 Embedding，计算：

- `Recall@K`：预期来源是否出现在前 K 个结果中。
- `MRR`：正确来源的排名是否足够靠前。

增加 `--generate` 后，还会调用聊天模型验证 `[来源 N]` 是否真的对应本次检索结果，并检查资料不足的问题是否明确拒答。

这一步的意义是把“感觉检索结果还可以”变成可重复的质量基线。以后修改切分、Embedding 模型或排序加分规则时，可以用同一组问题判断质量究竟提升还是下降。

## 测试结果

当前版本完成了以下验证：

- `cli-chat` Python 单元测试 36 项通过。
- `minimal-rag` 离线评测测试 2 项通过。
- Vitest 前端测试 20 项通过。
- VitePress production build 通过。

测试覆盖管理员认证隔离、登录限速、密码轮换、邀请码明文不落库、同步历史、滚动记忆、消息反馈、额度、SSE、人格选择、RAG 来源和人格锁定等关键边界。

## 总结

这一轮迭代最大的收获，是重新认识了“聊天历史”和“模型上下文”的区别。

聊天历史是需要持久化、分页、审计和受权限控制的数据；模型上下文只是从历史中按当前预算临时构造出来的一次输入。两者不能简单等同，更不能把数据库里的全部消息无条件发送给模型。

当前系统最终形成了这样的分层：

```text
完整原始历史：用于恢复、查看和重新构造上下文
滚动结构化记忆：保留较早对话中的关键事实与决定
最近完整问答：维持当前话题的细节和语言连续性
会话级人格：保证整个对话的行为模式一致
管理员与审计：管理同步数据，但不越过仅本机会话边界
```

它仍然是一个小型项目，但已经从“调用模型的页面”逐渐走向“有明确状态、记忆、安全和运维边界的聊天系统”。下一步可以继续验证真实长会话下的摘要质量，并基于用量指标调整记忆阈值、模型选择和成本策略。
